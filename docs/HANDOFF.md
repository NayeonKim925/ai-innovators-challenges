# REPLAN 인수인계

## 서비스

REPLAN은 승인된 범위 안에서 외부 변화를 자동으로 감시하고, 에이전트가 근거와 계산 도구로 일정의 숨은 영향을 미리 알리고 조사하며, 사람이 확인한 결과만 일정에 반영합니다. 날짜·비용·일정은 결정적 계산기가 계산하고, 에이전트는 등록 시 위험 브리핑, 새 공지의 분류, 통보 해석, 공지와 통보의 원인 연결, 통보에 없던 영향 조사, 확인 질문과 메일 초안을 맡습니다. 사람은 감시를 시작하고 해석을 확인하며, 조사를 시작하고 대응안을 승인해 새 일정 버전과 Excel로 내보냅니다.

화면은 **개요 → 일정 → 감시 → 변경 → 대응안 → 실행 → 이력** 순서입니다.

| 구성 | 하는 일 |
| --- | --- |
| 워커 (AI 아님) | 감시 계획을 활성화한 뒤 또는 **감시 시작** 때 등록 출처·공휴일·기상을 수집하고, 원문 해시로 실제 변화만 감시 피드에 등록(데모는 한 번의 수집을 시뮬레이션) |
| 사전 에이전트: 등록 시 브리핑 | 기준 일정 등록 때 속성(원산지·통관·인허가·야외) × 여유·주공정으로 위험 상위 3~5개. 계산기가 순위, 에이전트는 도구 확인 최대 3회와 L2 근거 연결 |
| 사전 에이전트: 변화 자동 추리기 | 새 공지를 관련 있음 / 확인 필요 / 무관으로 1회 분류, 별도 일일 한도 |
| 사후 에이전트: 협력사 통보 조사 | 사람이 시작. 대장을 읽고 같은 원인이면 연결, 관련 있음 + 사람이 고른 확인 필요 작업만 계산 |
| 리스크 대장 | 세 에이전트가 공유. 예상됨 → 신호 감지 → 발생 → 대응 중 → 종결과 변경 이력 |
| 사람 | 확인과 승인 |

언제 LLM을 부르는지는 [README의 에이전트 호출 원칙](../README.md#에이전트-호출-원칙)에 있습니다.

## X2 데모 실행

```cmd
scripts\demo.cmd
```

(macOS·Linux: `scripts/demo.sh`) 녹화된 LLM 응답을 재생하는 모드로 별도 스택을 띄웁니다. 키와 비용 없이 에이전트가 동작하고, 화면 위쪽에 "에이전트 켜짐 · 녹화본 재생 중(비용 0)"이 보입니다.

`http://localhost:3000` → 프로젝트 만들기 → **일정**에서 **hero 데모 기준 일정 연결** → **감시**에서 브리핑 확인(1순위: 중국산 통관 품목 P-A1·P-B·P-C, P-C 주공정 경고, 에이전트가 RS-019로 연결한 "중국 희토류 자석 수출 통제") → **감시 시작 · 데모 수집 시뮬레이션**(N-X2 수집, 자동 추리기 분류) → **변경** 받은편지함의 `대표 데모` 행([P-A1] 서보 모터 자석 부품 통관 지연) → **변경으로 등록** → **해석 확인 후 영향 분석** → **에이전트로 숨은 위험 조사** → **P-C도 해당함 · 일정 다시 계산** → 추천 조합 확인·승인 → **새 일정 버전 확정** → **Excel 다운로드**(마지막 완료일 2028-01-25). 화면별 확인 항목과 캡처는 [DEMO_GUIDE.md](DEMO_GUIDE.md)에 있습니다.

## 이번 변경 (PR #15, `claude/risk-register`)

### 추가된 것

- **감시 단계**: 일정과 변경 사이의 독립 화면. 일정 화면은 Excel 연결만 하고, 감시 화면에 브리핑·**감시 시작**·감시 피드(워커 신호 + 자동 추리기)·감시 계획 설정·리스크 대장·테스트용 공지 수집을 둠. `apps/web/app/stages.ts`의 한 목록이 사이드바·단계 표시·화면 순서를 정함. 기준 일정만 연결해서는 아무 신호도 들어오지 않고, `POST /api/projects/{id}/watch/start`가 hero 데모에서는 N-X2를 스캔과 같은 경로로 기록(수집 시뮬레이션), 다른 프로젝트에서는 활성화한 감시 계획으로 스캔.
- **등록 시 브리핑**(`services/api/app/briefing.py`): 계산기가 구매 품목과 작업을 원인별로 묶고 속성 수 × 여유 노출로 순위를 정함. 에이전트는 도구 확인 최대 3회(같은 원인 품목 찾기·작업 속성·여유)와 사례 검색 1회로 품목을 더하거나 근거와 함께 후보를 뺌. 추가 품목은 도구가 돌려준 것만, 순위·숫자는 계산기가 다시 매김. 기존 `watch_plan_enrich` 실행 자리(`baseline_briefing`)에서 돌고 감시 계획 보강도 같은 실행에서 함. 사람이 기다리는 실행에 순서를 양보함.
- **변화 자동 추리기**: `interpret_notice`가 관련 있음 / 확인 필요 / 무관과 대장 연결을 돌려줌. 등록 출처 공지이고 규칙 후보가 1개 이상일 때만 1회. 결과는 `event.auto_narrow`에 따로 저장해 `related_task_ids`를 바꾸지 않음(협력사 통보와의 X2 연결 유지). 사람이 시작하는 분석·조사와 **별도의 일일 한도**(`auto_usage_ledger`, `REPLAN_MAX_AUTO_TRIAGE_PER_DAY`). 사람이 시작한 분석은 이 결과를 다시 부르지 않고 씀.
- **리스크 대장**(`services/api/app/risk_register.py`, 표 `risks`): 브리핑이 '예상됨'으로 올리고, 자동 추리기가 같은 원인 공지를 '신호 감지', 조사 에이전트가 협력사 통보를 '발생'(외부 공지는 '신호 감지'), 사람이 조사 결과를 '해당함'으로 확인하면 '대응 중'. 에이전트는 상태를 앞으로만 옮기고, 사람은 `PATCH /api/projects/{id}/risks/{risk_id}`로 '종결'을 포함해 어떤 상태든 기록. 모든 변경은 누가·언제·어떤 근거로 했는지 이력에 남음.
- **받은편지함 모양**: 변경 화면의 합성 통보 선택을 보낸 사람·제목·받은 시각·미리보기 목록과 본문 보기로 바꿈. 행은 `InboxMessage` 한 가지 모양(`apps/web/app/inbox.tsx`)이라 메일 연결은 데이터 출처만 바꾸면 됨. 데모 메시지에 제목을 추가. 외부 공지는 받은편지함이 아니라 감시 화면에서 불러옴.
- **조사를 전제 조건 방식으로**: 조사 프롬프트는 단계 순서 대신 사람이 필요로 하는 결과(흡수 여부, 흡수하지 못하면 최악 조건과 행동 기한)를 말하고, 도구가 전제 조건만 막음: 원문에 적힌 기간·날짜만 사용, 여유 확인 전 조건부 계산 금지, 통보에 없던 품목을 사람이 확인하기 전 대응안 비교 금지. 한 턴에 여러 도구를 요청하면 그 턴에 모두 실행. L2 사례 검색은 정해진 검색어 목록(`CASE_QUERIES`)에서만 고름.
- **'확인 필요'는 사람이 고른 것만 계산**: 외부 공지 조사는 자동 추리기의 '관련 있음' 작업과, 카드에서 사람이 체크한 '확인 필요' 작업(`include_task_ids`)만 계산. 나머지는 도구가 계산을 거절함.

### 바뀐 원칙

예전에는 "자동 감지는 LLM을 부르지 않는다"였습니다. 감지된 공지는 키워드가 맞은 규칙 후보(N-X2는 29개)만 보여 줘서, 사람이 모두 읽고 조사할지 정해야 했고, 기준 일정의 위험은 첫 통보가 올 때까지 아무도 알려 주지 않았습니다. 이제 미리 알리기 위해 두 곳에서 LLM을 부릅니다: 기준 일정 등록 때 브리핑 1회 실행, 새 공지마다 자동 추리 1회. 대신 경계를 둡니다.

- 자동 추리는 규칙 후보가 없으면 부르지 않고, 사람의 한도와 따로 세며, 한도를 넘으면 규칙 결과만 남기고 화면에 표시.
- 둘 다 일정·비용을 바꾸지 않고, 조사를 자동으로 시작하지 않음(버튼만 표시).
- 에이전트가 쓰는 숫자·순위는 계산기가 다시 매기고, 엑셀에 없는 원인은 읽은 L2 사례와 함께만 붙음.

### 데이터 변경

- **구매 목록을 중립 사실로**: hero 워크북 Procurement 시트의 허가·인증 칸에서 "중국 희토류 수출 허가(선적마다)"를 빼고 원산지 증명·교정 성적서만 남김. P-A1 품목명에 "희토류 자석 포함"을 더함. 브리핑 규칙은 원산지·통관으로만 묶고, "중국 희토류 자석 수출 통제"라는 원인은 에이전트가 RS-019를 읽고 연결(`linked_cause`, 읽은 사례가 없으면 버림). 브리핑 1순위는 그대로 중국산 통관 품목(P-A1·P-B·P-C).
- **브리핑 근거 기준일 분리**: 일정 기준 시점(작업 상태)은 2025-08-20 그대로, 브리핑의 L2 근거 기준일만 2025-10-20(`evidence_as_of_date`, `data/hero_demo/supplier_messages.json`). RS-019(2025-10-15)가 참고가 아니라 근거로 인용됨. 기준 시점 자체를 옮기면 통보 H01~H08(2025-08-21~25)이 기준 시점보다 앞서게 되어 이 방식을 택함. X2·H04 계산 결과는 그대로.

### 중간에 고친 버그

- **녹화·재생 요청 불일치**: 외부 근거 해석이 `record` 모드에서는 인용 문단을 넣고 `replay` 모드에서는 넣지 않아, 녹화한 요청이 재생되지 않았음. 인용 문단은 `live`에서만 쓰도록 고침.
- **M1 통보가 대장에 '발생'으로 기록됨**: X2-대조에서 에이전트가 외부 공지의 원인을 근거로 대장을 연결해, 원인이 다른 협력사 통보가 '발생'으로 찍혔음. M1로 멈춘 협력사 통보는 대장에 기록하지 않음.
- **브리핑 중복 표시**: 위험 키 이름을 바꾸면서 품목의 필요 작업이 작업 행으로 한 번 더 나와 T051 경고·선제 행동이 중복됐음. 화면에는 품목 아래 한 번만 표시(에이전트가 읽는 내용은 그대로).
- **대기 시간 초과**: 후보 29개를 분류하는 자동 추리 호출이 30초 제한에 걸려 실패 → 분류 호출 150초. 조사의 마지막 응답도 길어 조사 호출은 90초.
- **조사가 '확인 필요'까지 계산**: X1-B에서 T012 등까지 계산하고 M5로 끝남 → 위의 '사람이 고른 것만 계산' 규칙.
- **브리핑이 사람의 분석보다 먼저 잡힘**: 대기열에서 브리핑 실행이 사람이 기다리는 분석을 막음 → 브리핑은 순서를 양보.
- **테스트 시간 증가**: 기준 일정마다 여유 계산으로 전체 테스트가 45초 → 174초 → 주공정 작업은 한 번에 판정하고 같은 일정은 다시 계산하지 않도록 캐시.
- 화면: 확인 필요 체크박스 크기, 좁은 열의 받은편지함 배치.

| X1-B | M2. 자동 추리기가 T013을 확인 필요로 두어, 흐름이 사람처럼 T013을 골라 조사. T013만 계산해 여유 168일로 45일 흡수 |

### 알려진 한계

- **자동 추리기 분류가 녹화마다 달라질 수 있음**: 같은 X1-B 공지가 한 녹화에서는 T013을 관련 있음, 다른 녹화에서는 확인 필요로 분류. '확인 필요'가 많음(N-X2 15건, 외부 공지 11건, X1-A 9건). 조사는 확인 필요를 자동으로 계산하지 않으므로 관련 있음이 0건이면 사람이 고르거나(X1-B) 적용 작업을 묻고 멈춤(X1-A).
- **L2 사례**: 저장된 19건 중 발행일과 링크가 있는 10건만 인용됨. 통관 자체의 사례가 없어 물류 검색은 반도체 부족 사례를 돌려줌.
- **N-X2는 합성**: 감시 시작이 합성 공지를 수집 경로로 넣은 것이며, 실제 감시가 이런 공지를 찾는지는 확인하지 않음.
- **검색 도구의 자유 문장 한계**: 저장 사례는 영문 분류어로만 검색되어 자유 문장(예: "중국 희토류 자석 부품")은 0건. 브리핑과 조사는 정해진 검색어 목록에서만 고르게 해 우회했고, 계산된 대응안 설명 에이전트의 사례 검색은 여전히 위험 유형 단어로만 찾음.
- **Gmail 미연결**: 받은편지함은 합성 메일만 보여 줌. 메일 연결 정보는 고급 설정에 저장만 되고 수신하지 않음.
- **한도 단위**: 일일 한도는 호출이 아니라 실행 단위(F29).

## 외부 변화 감시가 가져오는 것

감시는 사람이 감시 화면의 **감시 계획 설정**에서 제안을 수락·제외하고 활성화해야 주기적으로 동작합니다. 들어온 등록 출처 공지는 변화 자동 추리기가 1회 분류하고(별도 일일 한도), 조사는 사람이 시작할 때만 합니다.

| 대상 | 실제로 가져오는 것 |
| --- | --- |
| 날씨 | Open-Meteo 예보(현장 좌표·풍속·강수 기준, 선택한 야외 작업에 연결). 선택 시 과거 기상 통계 |
| 공휴일 | Nager.Date 국가 공휴일 |
| 공식 공지 | 등록한 HTTPS 페이지·RSS. 허용 호스트만(`REPLAN_ALLOWED_SOURCE_HOSTS`, 기본 `environment.ec.europa.eu`), 기본 제안은 EU 환경총국 뉴스 페이지 |
| L2 실제 기사 | 가져오지 않음. 저장소의 정리된 사례 모음(`data/l2_risk_signals/risk_signals.json`)을 로컬에서 검색 |

데모의 N-X2는 실제로 수집한 공지가 아닙니다. **감시 시작**이 합성 공지를 등록 출처 기록 경로(`environment.ec.europa.eu/news_en` 출처, `합성` 표시)로 넣어 실제 감시와 같은 방식으로 저장·자동 분류되게 했습니다.
